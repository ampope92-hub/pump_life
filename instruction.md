We rebuild and lease centrifugal pumps, and the mechanical seal is what kills them. I need two numbers for a batch of pumps we're quoting service contracts on, because right now we're guessing on both. `/app/data/train.csv` is everything the maintenance system knows about the pumps we've had in service — how each one was set up and run, and where it got to. `/app/data/test_features.csv` is the quote batch, same setup columns. `/app/data/README.md` explains the columns and how the maintenance export was pulled.

Our tooling is Rust, so this has to live there — there's a Cargo project started for you at `/app/predictor` with `smartcore` and `csv` already wired into `Cargo.toml`. Fill in `src/main.rs` so that running it reads both CSVs, fits whatever model you think will hold up, and writes `/app/predictions.csv` with exactly three columns, `pump_id`, `life_days` and `service_days` — one row for every `pump_id` in `test_features.csv`, header included, any order. `life_days` is the seal life you expect from that pump in days, counted from install. `service_days` is what we quote as its service interval: the age we'd schedule the seal change at, chosen so that no more than **10%** of pumps set up and run like that one will have failed before we get to them. The box is offline: the crates already in `Cargo.toml` are cached locally at the versions pinned in `Cargo.lock` so builds work, but you can't pull in new ones.

What it has to do, rather than how we score it. `/app/predictor` must produce the file itself on a clean build: a fresh `cargo run --release` in that directory, with no `predictions.csv` present, has to read both CSVs, fit, and write the output. Don't leave results checked in — whatever is sitting at `/app/predictions.csv` gets cleared before that run. We also point the same program at other quote batches in this format, so it has to fit from whatever is in `/app/data` when it runs; predictions worked out once and written into the source as constants are no use to us.

The numbers it writes have to hold up against what the pumps actually did. `life_days` needs an R² of at least 0.36 against the real seal lives. `service_days` has to land between 8% and 12% failed-before-quoted across the batch — within 2 points of the 10% you were asked for — and separately between 5.5% and 14.5% inside each of the smoothest, middle and roughest thirds by vibration, because an interval that is only right on average is one we can't schedule from. Neither column may come out flat: across the batch each has to span more than a tenth of its own mean, or it isn't a per-pump quote.
